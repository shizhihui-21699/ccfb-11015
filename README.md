# 车辆里程真实性鉴定工具（mileage-audit）

读取车辆各控制单元（ECU）数据与历史维保/年检记录，综合推断真实行驶里程、
识别调表并输出**可质证的证据链报告**。纯 Kotlin/JVM 实现，规则引擎确定性执行。

## 为什么这样设计——对应鉴定实务中的四个难点

| 难点 | 本项目的应对 |
| --- | --- |
| 不同品牌车型数据存放方式不同 | 采集层 SPI（`VehicleDataAdapter`）把各品牌私有协议/UDS 诊断统一映射为标准模型 `EcuReading`/`MileageEvent`；引擎只依赖标准模型，新增品牌只写适配器，不改规则 |
| 调表者把能想到的单元一起改 | 规则不依赖单一数据源，要求**多源独立印证**；全车同步刷写后，历史单据（R3/R4）与工作小时（R2）仍可戳穿；"读数一致"只给弱负分，不能自证清白 |
| 单元更换/维修清零过 | `EcuStatus` 三态（ORIGINAL/REPLACED/UNKNOWN）+ R6 显式留痕：换件模块排除出硬证据，状态不明模块只作软证据不定下限，从机制上压制误报 |
| 维保记录缺失或本身伪造 | 记录缺失 → 出具 `INCONCLUSIVE` 而非猜测；伪造 → R5 用同期跨渠道对撞识别，低可信单据标注"疑似伪造"，但不越权替人工认定事实 |
| 结论要经得起买卖双方质疑 | ① 每条结论带证据锚点（ECU ID/事件 ID）与原始报文 SHA-256；② 规则纯函数、同案同判；③ 输入指纹 + 报告哈希链证明未被事后篡改；④ 只主张"真实里程下限"，不夸大 |

## 模块结构

```
core/       领域模型 + 六条鉴定规则 + 融合引擎 + 指纹/哈希（不依赖任何采集实现）
adapters/   采集 SPI 与案卷 JSON 导入适配器（含原始证据哈希校验、目录穿越防护）
cli/        命令行入口，输出人类可读报告 + 结构化 JSON
samples/    调表/未调表两套示例案卷及模拟原始证据文件
```

### 六条规则（互相独立、各自单测、可逐条质证）

| ID | 规则 | 事实依据 |
| --- | --- | --- |
| R1 | 跨 ECU 里程比对 | 独立模块读数高于表显的部分是调表硬下限；分硬/软证据 |
| R2 | 工作小时/计数器反推 | 里程 ≈ 小时 × 平均速度，乘 0.8 保守系数防工况误判 |
| R3 | 历史时序矛盾 | 真实里程随时间单调不减，倒挂即异常 |
| R4 | 历史里程高于当前表显 | 过去的里程不可能大于现在（最朴素最难辩驳） |
| R5 | 多来源单据冲突 | 同期跨渠道记录对撞，识别伪造保养单 |
| R6 | 模块更换/清零留痕 | 防误报规则，记录证据取舍过程 |

### 融合与结论分档

- 正向（指向调表）与负向（指向真实）证据**分别加权**，高可信证据权重数量级更高
  （密码学级 10 > 高 6 > 中 3 > 低 1 > 不可信 0.2）
- 存在硬矛盾时负向证据权重封顶 25%，且正向证据主导融合（80%）——
- "未见异常"不能线性对冲掉可验证的矛盾事实
- 五档结论：`CONFIRMED_TAMPERED / LIKELY_TAMPERED / INCONCLUSIVE / LIKELY_GENUINE / CONFIRMED_GENUINE`，
  确认级结论要求多证据组或单组多模块印证，杜绝单条证据一锤定音

## 构建与运行

需要 JDK 21（本机通过 `JAVA_HOME` 指向 Homebrew openjdk@21 即可）：

```bash
# 全量测试（10 个引擎场景 + 4 个适配器安全测试）
gradle test

# 构建 CLI
gradle :cli:jar

# 鉴定调表样例（退出码 2）
java -jar cli/build/libs/cli-0.1.0.jar \
  samples/case_tampered.json --artifacts samples/artifacts --out report.json

# 鉴定未调表对照样例（退出码 0）
java -jar cli/build/libs/cli-0.1.0.jar samples/case_genuine.json
```

退出码：`0`=未调表，`2`=调表，`3`=证据不足，`4`=输入错误（含证据哈希校验失败）。
同一案件多次鉴定用 `--prev-hash <上一份报告哈希>` 形成哈希链。

## 证据完整性机制

1. 每条 `EcuReading`/`MileageEvent` 强制携带原始报文或单据的 SHA-256
2. 导入适配器可对 artifacts 目录中的原始文件重新算哈希，不符即**拒绝导入**
3. 案卷整体经规范化 JSON（键排序）后生成输入指纹，字段顺序不影响指纹
4. 报告对除自身哈希外的全部字段取 SHA-256，支持跨次鉴定的哈希链

## 后续落地真实诊断的路线

1. 在 `adapters` 下按品牌实现 `VehicleDataAdapter`（UDS/KWP2000/厂家私有协议），
   原始 DID 报文先落盘再算哈希，映射到标准模型
2. 维保/年检/保险渠道对接实现为记录类适配器，`verified` 与 `trustLevel`
   必须由渠道校验结果决定，禁止人工直接给高可信
3. 规则参数（饱和阈值、噪声带、平均速度假设）按车型/用途校准，
   每次调整伴随回归测试，保证历史案件结论可复现
4. 报告 JSON 字段保持稳定并版本化，便于司法/消保场景长期归档
